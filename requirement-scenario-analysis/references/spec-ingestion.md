# 从 spec / PRD 文档提取场景

Phase 1 的输入处理专用。配合 `scenario-dimensions.md` 使用：**spec 负责给出「明写了什么」，维度库负责补齐「没写但会发生什么」**。两部分的来源必须在场景清单里分开标注。

## 一、输入识别（按优先级，命中即停）

1. 用户显式给出的文档路径（`.md` / `.markdown` / `.txt` / `.yaml` / `.json` / `.rst` / `.adoc`）
2. 用户消息里出现的文件路径
3. 工作区内自动发现常见 spec 位置：`specs/`、`docs/specs/`、`requirements/`、`PRD`、`spec.md`、`需求文档`、`设计说明` 等命名
4. 以上都没有 → 走「纯需求描述」路径，按 SKILL.md Step 1 处理，**不得假装读过 spec**

多条文档时逐份读取，分别记录来源标识；不要把多份文档的规则合并成一份「隐式共识」，冲突处按第五节处理。

**反臆造硬规则**：字段、状态、枚举、阈值、错误码、接口名只能来自实际读到的内容。spec 没写就写【未提供】，禁止凭常识补一个字段或规则再当成规格依据。读 spec 时同样禁止引用聊天历史里的「之前的版本」当作当前 spec 内容。

## 二、从 spec 中抽取什么

| 抽取项 | 在 spec 里找什么 | 转成什么 |
| --- | --- | --- |
| 验收条件 | Given/When/Then、`AC-xx`、`FR-xxx`、验收标准、成功定义 | `[Source]` 业务主场景，编号原样保留 |
| 业务规则与阈值 | 「满 X」「不超过 Y」「至少 N」「连续 M 天」「T+1」 | `[Source]` 规则本身 + `[Source+Derived]` 阈值±1 类边界 |
| 字段与约束 | 必填、唯一、枚举、长度、格式、默认值、可空性 | `[Source]` 校验场景与边界种子 |
| 状态与流转 | 状态枚举、状态图、允许的流转、终态 | `[Source]` 状态边界与非法流转 |
| 角色与权限 | 角色清单、数据范围、租户、审批层级 | `[Source]` 角色差异场景 |
| 入口与集成 | 页面、API、定时任务、导入、消息、Webhook、下游 | `[Source]` 多入口一致性种子 |
| 明确排除项 | 「不在本次范围」「v2」「由框架/中间件/ORM/网关统一处理」「沿用现有逻辑」 | Spec Exclusions，见第四节 |
| 含糊与矛盾 | 「尽快」「正常情况」「原则上」「等」「通常」；示例与规则不一致 | `⚠️ SPEC AMBIGUITY`，见第五节 |
| 示例数据 / payload | 请求样例、表格样例、边界举例 | 逐条跑规则 dry run，检查样例本身是否违反规则 |

抽取结果先落成一张「spec 元素索引」：元素类型、原文要点、所在章节或编号。场景清单的来源列引用这张索引，不写「根据需求文档」这种无法定位的话。

## 三、来源标注（每条场景必填）

| 标注 | 含义 | 写法示例 |
| --- | --- | --- |
| `[Source]` | spec 明写，可直接指到章节或编号 | `[Source] spec §3.2 / AC-07` |
| `[Source+Derived]` | spec 给了规则，具体取值由本 skill 派生 | `[Source+Derived] spec §4 阈值 100 → 派生 99/100/101` |
| `[Inferred]` | spec 未写，由维度库补齐 | `[Inferred] F3-重复与重试` |
| `[Inferred]` + 缺口 | 补齐时发现 spec 缺关键定义 | `[Inferred] F2-时间边界；spec 未定义跨账期口径【未提供】` |

规则：

- **spec 通常只写主流程和少量约束，边界与特殊场景绝大多数是 `[Inferred]`**。这是正常结果，不是缺陷；但绝不能把补出来的写成 spec 结论。
- `[Inferred]` 必须指到 `scenario-dimensions.md` 的具体组（F1 / F2-某组 / F3-某组），便于反查为什么补这条。
- 纯需求描述路径下，全部场景标 `[Inferred]`（或 `[Source] 用户口述`），同样不许留空。
- 来源列为空的场景视为不合格输出。

## 四、Spec Exclusions（排除与留痕）

只有 **spec 明确声明** 才能排除场景，不能因为「看起来不重要」「一般不会发生」就跳过。

常见声明词：

- 归属类：「由网关 / 中间件 / ORM / 校验框架 / 公共组件统一处理」「已有基础能力保证」
- 范围类：「不在本次范围」「out of scope」「v2 / 后续迭代」「暂不支持」「本次不改」
- 沿用类：「沿用现有逻辑」「行为不变」「保持兼容」

处理：

1. 对应维度的场景不展开，或降级成**一条核对项**（例如「确认该公共校验组件确实接入了本次新增入口」）。
2. 必须写入 **Scope Reduction Log**：被排除的场景族、依据（spec 章节 + 原文片段）、剩余待核对项。
3. 排除是「生成约束」，不是事后删除。输出前复核一遍，确认被排除的场景没有从别的维度绕回来。
4. **禁止静默省略**：没出现在场景清单里、也没出现在留痕表里的场景族，视为漏场景。

注意「由公共组件处理」只排除该组件职责内的场景，不排除它在**新入口 / 新数据态**下是否生效——后者仍要作为核对项保留。

## 五、歧义与矛盾

- **模糊词**：标 `⚠️ SPEC AMBIGUITY`，场景按**更严解释**生成（报错 / 拒绝 / 不产生副作用 优先于 放行），同时进「待确认问题」。
- **规则互相冲突**：不替业务选边。标 `⚠️ SPEC AMBIGUITY`，按更严解释生成一条场景，并列出两个选项及各自对预期结果的影响。例：spec 一处写「重复请求返回原结果」，另一处写「同键禁止重复」，两者都要列出。
- **示例与规则冲突**：不擅自改示例、也不擅自改规则，标为矛盾并写清冲突点。
- **spec 与代码不一致**（Phase 2 才发现）：显式报告分歧，不擅自把 spec 或代码任何一方当权威，该场景判 ❓ 并写明需要谁确认。

所有歧义项在输出中有独立小节，包含：编号、冲突/未定义之处、按更严解释生成的场景 ID、对应的待确认问题编号。

## 六、Blocking Questions（只问必要的）

只有「不回答就无法写出该场景的预期结果」的问题才问，最多 3 个。其余记为显式假设并标【待确认】。问题要指向具体 spec 章节与具体场景 ID，不要问「还有别的补充吗」这类开放题。

## 七、稳定 ID 与双向追溯

- spec 里的 `AC-xx` / `FR-xxx` / 章节号**原样保留，不重命名、不重新编号**。
- 场景 ID（`B01` / `E01` / `S01` 等）一经分配**不改号、不复用**；后续增删场景只追加新号。
- 正向：每个 `[Source]` 场景能回溯到至少一个 AC / 章节；spec 中每条 AC 至少映射一个场景，映射不到的要写明理由。
- 反向：每条场景都能回答「它来自 spec 哪一条，或来自哪个维度组」。
- Phase 2 覆盖矩阵、待补清单、❓ 项、待确认问题、测试用例映射，**全部引用同一个场景 ID**，不另起一套编号。

## 八、边界：本 skill 不做 PRD 评审

读 spec 时发现字段缺失、规则未定义、示例冲突，可以在输出末尾附一节「影响场景枚举的 spec 缺口」，只列影响场景判断的缺口。**不要**输出文档质量评分、缺陷风险矩阵或 PRD 改写建议——那是别的工具的职责。
