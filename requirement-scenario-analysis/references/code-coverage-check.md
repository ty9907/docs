# 场景 → 代码适配性核验方法

Phase 2 专用。**本阶段只判定「场景有没有被代码处理、处理得全不全」，不预测缺陷、不评估风险、不判断哪里会崩。**

## 〇、稳定 ID 与双向追溯（先于检索执行）

- 沿用 Phase 1 的场景 ID（`B01` / `E01` / `S01` …），**不另起编号、不改号、不复用**。
- spec 中的 `AC-xx` / `FR-xxx` / 章节号原样保留，写进覆盖矩阵的「来源」列，便于回查。
- 每个 `[Source]` 场景能回溯到至少一个 AC / 章节；spec 中每条 AC 至少映射一个场景，映射不到的在结论里写明理由。
- 覆盖矩阵、待补清单、❓ 项、待确认问题、测试用例映射全部引用同一场景 ID，不出现第二套编号。
- 若 Phase 1 的 `[Inferred]` 场景在代码里找不到处理，判 ❌ 时注明「spec 未定义该场景，来自维度组 F3-xx」，避免把规格缺口误判成实现缺陷。

## 一、把场景转成检查点

逐条读 Phase 1 场景的「代码检查线索」列，转成 1–3 个可检索的检查点。

| 场景要素 | 代码里应当出现 | 常用检索关键词 |
| --- | --- | --- |
| 前置条件含「无数据 / 空态」 | 空集合判断、首次初始化、默认值 | `isEmpty`、`size() == 0`、默认值常量、`Optional`、初始化分支 |
| 边界值 / 阈值 | 阈值常量与比较分支（含不含等号） | 阈值常量名、`>=`、`>`、`<=`、`compareTo`、`BETWEEN` |
| 时间边界 | 时间窗口计算、时区处理、闭开区间 | `LocalDate`、`between`、`startOfDay`、`ZoneId`、`>= start && < end` |
| 状态前提 | 状态枚举判断、流转守卫 | 状态枚举名、`switch`、`if (status ==`、状态机配置 |
| 重复 / 重试 | 幂等键、执行记录判重、唯一约束 | `idempotent`、幂等字段、唯一索引、`job_log`、`ON CONFLICT` |
| 并发 | 锁、乐观锁版本、原子操作 | `synchronized`、`version`、`@Version`、分布式锁、`CAS` |
| 部分失败 | 事务边界、失败清单返回、补偿入口 | `@Transactional`、事务注解、批量回滚标记、补偿方法名 |
| 权限差异 | 统一权限过滤封装、角色判断 | 权限注解、拦截器、`DataScope`、租户字段、角色枚举 |
| 缓存相关 | key 构造维度、失效点 | `redis`、`cache`、`evict`、key 前缀拼接 |
| 配置 / 灰度 | 开关判断且关闭分支等价旧行为 | feature flag 名、配置 key、灰度命中判断 |
| 多入口一致性 | 同一逻辑被各入口复用或各入口都有对应处理 | 接口名、定时任务方法、导入方法、消息消费者，逐一比对 |
| 撤销 / 回滚 | 逆向处理、下游撤回 | `cancel`、`revoke`、`rollback`、补偿消息 |
| Spec Exclusion 核对项 | 被声明「由公共组件处理」的能力确实接入了新入口 | 组件名、拦截器注册、配置开关、切面 |

## 二、检索范围清单（别只查主入口）

对每个检查点，至少覆盖这些位置：

1. 主流程 service / handler 的判断分支
2. 其他写入点与读取点（定时任务、导入、消息消费、后台运维、导出）
3. DTO / VO 的构造与序列化（字段默认值、未知字段策略）
4. 数据访问层（SQL 条件、聚合口径、权限过滤是否统一）
5. 配置与常量（阈值、开关、枚举、错误码）
6. 事务与异常处理（边界、重试、补偿）
7. 缓存与消息（key 维度、失效、重复消费）
8. 权限切面与拦截器
9. 测试代码（是否已有对应用例，可作覆盖证据的辅助）

## 三、四档判定标准与证据要求

| 判定 | 含义 | 必须给出的证据 |
| --- | --- | --- |
| ✅ 已适配 | 找到明确处理，且条件与场景前提完全一致 | `文件:函数` + 关键条件表达式 / 分支代码 |
| ⚠️ 部分适配 | 有相关处理，但条件不全、只覆盖部分入口、或只覆盖部分数据态 | 已有处理的证据 + 明确写出缺哪部分（如「只判 `>` 未含 `=`」「仅页面入口有，定时任务入口无」） |
| ❌ 未适配 | 检索无结果，或场景前提会落入不匹配的分支 | 已执行的检索式 + 结论；无结果也要列检索式 |
| ❓ 无法确认 | 代码不可读、动态派发、配置 / 数据驱动、依赖外部系统行为、spec 与代码分歧 | 写明缺什么（配置项实际取值、外部契约、运行时数据、需要谁确认），以及拿到后可执行什么检索 |

证据硬要求：

- 引用 `文件:函数` 必须来自实际检索结果，禁止凭印象编造路径。
- 判定不能用「看起来有处理」「应该有」这类措辞。
- 同一段代码可以支撑多个场景，但每个场景要单独写明它命中了哪个条件。
- 测试代码中的用例可作为辅助证据，但不能替代实现代码。
- **spec 与代码不一致时显式报告分歧**，判 ❓，不擅自把 spec 或代码任一方当权威，写明需要谁确认。

## 四、常见误判（输出前逐条排除）

1. **把「有判空」当成覆盖所有空态**：只判了入参为 null，没判历史数据字段为 null / 空集合 / 查询结果为空，应判 ⚠️。
2. **只查主入口**：页面处理了，定时任务 / 导入 / 消息消费没处理，应判 ⚠️ 并列出漏掉的入口。
3. **把兜底 catch 当成场景已适配**：捕获异常只是不报错，不等于按场景预期处理了，应判 ⚠️ 或 ❌ 并说明预期结果未满足。
4. **把配置驱动当成未适配**：配置值决定行为时，看不到值应判 ❓，不是 ❌。
5. **把边界值合并**：阈值 `>` 与 `>=` 是不同场景，只覆盖其一应判 ⚠️，不能一并打 ✅。
6. **把「重复数据」当一种**：完全重复、同键不同值、格式差异重复需分别判定。
7. **把历史报表 / 已发通知漏掉**：场景副作用里列了，就要去核对对应代码，否则该场景判 ⚠️。
8. **用风险语言代替覆盖判定**：写「可能有并发问题」不合格，要写「并发场景：❌ 未适配，未检索到幂等键或锁」。
9. **把规格缺口当成实现缺陷**：`[Inferred]` 场景在代码里没处理，且 spec 也没定义时，判 ❌ 但必须注明这是「spec 未定义 + 代码未覆盖」，不能直接写「实现有 bug」。
10. **擅自裁决 spec 与代码分歧**：看到代码行为与 spec 不符就按代码改判定，应判 ❓ 并报告分歧。

## 五、代码不可读时

不输出覆盖矩阵，改为输出「可执行的检查表」：每个场景一行，给出应有什么处理、该搜什么关键词、由谁在哪个仓库执行。所有判定列留空并标 ❓，不猜测代码行为。场景 ID 仍沿用 Phase 1 编号。

## 六、输出顺序

覆盖矩阵 → 三类覆盖率统计 → ⚠️ / ❌ 待补清单（按场景编号排序）→ ❓ 项所需信息 → spec 与代码分歧项（如有）→ 结论（仅陈述覆盖情况，不做风险评级）。
