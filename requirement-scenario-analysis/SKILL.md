# 业务场景枚举与代码适配性核验

## Overview

两个阶段，先后关系不可颠倒：

- **Phase 1（必做）**：把需求展开成三类场景清单——业务主场景、边界场景、特殊场景。每条场景带前置条件、操作、预期结果、副作用、**来源标注**和一条**代码检查线索**。产出是一份可直接当检查表用的清单。
- **Phase 2（按需）**：拿这份清单逐条核对当前代码是否处理了该场景，输出覆盖矩阵与代码证据。判定的是「有没有适配 / 覆盖得全不全」，不是「哪里会崩」，也不预测缺陷。

核心原则：**先把场景列全，才谈得上核对代码**。用户没给场景清单时，先完成 Phase 1 再进入 Phase 2。

输入可以是**已有 spec / PRD 文档**，也可以是**一段需求描述**。走文档路径时，spec 只提供「明写了什么」，边界与特殊场景主要由维度库补齐，两者必须在输出里区分开——见 `references/spec-ingestion.md`。

## 三类场景的定义（务必区分）

| 类别 | 定义 | 典型来源 |
| --- | --- | --- |
| 业务主场景 | 需求要支持的常规业务动作，不同角色 / 对象状态 / 入口下的正常路径 | 角色、单据状态、动作类型、渠道、数据来源 |
| 边界场景 | 输入或状态处在合法范围边缘，值本身合法但贴近阈值 | 0 / 空 / 最大值 / 长度上限 / 精度、刚好一页或跨页、临界时点、首末节点、差一点满足条件 |
| 特殊场景 | 非典型但真实会发生，由存量、时序、协同、环境、配置引发 | 无历史数据、历史 / 脏 / 软删数据、重复与重试、并发、时序颠倒、部分失败、依赖异常、权限差异、撤销回滚、开关灰度、多入口 |

边界与特殊不重叠：**边界是「值在范围边缘」，特殊是「环境和时序让同一份输入处在不同的处境」**。不要把并发、重试、历史数据塞进边界类。

## 何时使用

- 拿到一份 spec / PRD / 需求文档，想把里面的业务、边界、特殊场景提取成清单
- 需求评审 / 写 PRD 前梳理场景，防止漏场景
- 提测前生成检查表与测试用例
- 拿到一段现有代码，想知道它覆盖了哪些场景、漏了哪些
- 接手老功能，用场景清单反推实现完备性

## Phase 1 · 场景枚举

### Step 0 · 确定输入并读取 spec（有文档时必做）

按 `references/spec-ingestion.md` 第一节识别输入：用户给的路径 → 消息中的路径 → 工作区内常见 spec 位置 → 都没有则走「纯需求描述」路径。**不得假装读过 spec**。

读到文档后，抽取验收条件、业务规则与阈值、字段约束、状态流转、角色权限、入口集成、明确排除项、含糊与矛盾处、示例数据，落成「spec 元素索引」。字段 / 状态 / 枚举 / 阈值 / 错误码只能来自实际读到的内容，没写就标【未提供】，禁止凭常识补一个再当成规格依据。

### Step 1 · 锁定需求边界

确认一句话目标、主体实体、触发入口、成功定义、涉及的角色与状态。走文档路径时以 spec 元素索引为准；信息不足时最多问 3 个 Blocking Question（只问「不答就写不出场景预期结果」的），其余写显式假设并标【待确认】。

### Step 2 · 先列状态变量，再组合场景

读取 `references/scenario-dimensions.md`，逐轴过一遍维度库，挑出本次相关变量及取值。spec 中出现的规则、阈值、状态枚举也要进状态变量清单。**先产出状态变量清单，再产出场景清单**——场景是变量组合的结果，不靠一条条想。组合后裁剪，写明剔除理由（物理上不可能 / 被约束禁止 / 等价合并）。「无数据」必须作为显式状态列出，不是缺省背景。

spec 明确声明排除的场景族走 `references/spec-ingestion.md` 第四节，记入 Scope Reduction Log，不在此处静默丢掉。

### Step 3 · 三类场景分层展开

按最小配额展开，任何一类都不允许为空：

- **业务主场景**：覆盖主要角色 × 主要对象状态 × 主要入口的正常路径；spec 的 AC / FR 逐条映射进来。
- **边界场景**：至少核对 数值 / 集合边界、时间边界、状态边界、首末次 四组，命中的逐条展开，不命中的写「不适用 + 理由」。
- **特殊场景**：至少核对 存量数据、重复与重试、并发、时序、部分失败、依赖异常、权限差异、撤销回滚、配置差异、多入口 十组，相关的逐条展开，不相关的写「不适用 + 理由」。

spec 通常只写主流程，**边界与特殊场景绝大多数靠维度库补齐**，这部分一律标 `[Inferred]` 并指到具体维度组。

### Step 4 · 每条场景写八列

| 编号 | 类别 | 来源 | 前置条件 | 输入与操作 | 预期结果 | 副作用 / 关联影响 | 代码检查线索 |
| --- | --- | --- | --- | --- | --- | --- | --- |

- **来源**：`[Source] spec §X / AC-xx`、`[Source+Derived] spec §X 阈值 N → 派生 N±1`、`[Inferred] F3-重复与重试`。规则见 `references/spec-ingestion.md` 第三节，不允许留空，不允许把补齐的写成 spec 结论。
- **代码检查线索** = 该场景在代码里应当出现的判断 / 分支 / 守卫 / 默认值 / 兜底，加上可检索的关键词（字段名、状态枚举、阈值常量、判空、唯一键、幂等键、事务注解、缓存 key、权限注解、错误码）。这一列是 Phase 2 的桥梁，不允许留空。

规格矛盾或关键定义缺失时，标 `⚠️ SPEC AMBIGUITY`，按**更严解释**（报错 / 拒绝 / 不产生副作用优先）生成场景，并同步进「待确认问题」；不替业务拍板。

按 `assets/scenario-matrix-template.md` 第一部分输出。

### Step 5 · 自检

按 references 的漏场景自检清单逐条打勾；确认三类配额都满足；确认每条场景都有来源标注、都能独立判定「代码处理了 / 没处理」；确认排除项已留痕、歧义项已单列、场景 ID 已稳定分配。

## Phase 2 · 代码适配性核验（代码可读时执行）

### Step 6 · 把场景转成检查点

每条场景转成 1–3 个可检索的检查点，**沿用 Phase 1 的场景 ID，不另起编号**。检索范围包括但不限于：判断分支、守卫条件、默认值、枚举、错误码、事务与重试、缓存、权限过滤、定时任务、消息消费、导入、导出。方法与检索式见 `references/code-coverage-check.md`。

### Step 7 · 逐条核验并给证据

判定只用四档：

- ✅ **已适配**：找到明确处理，且条件与场景前提一致，附 `文件:函数` + 关键条件表达式。
- ⚠️ **部分适配**：有相关处理但条件不全，或只覆盖部分入口，写明缺哪部分。
- ❌ **未适配**：检索无结果，或该场景的前提会落入不匹配的分支。
- ❓ **无法确认**：代码不可读、动态派发、配置驱动，写明还缺什么才能确认。

**禁止**把判定写成「这里可能会崩 / 有风险」；只回答「这个场景有没有被处理、处理得是否完整」。引用文件 / 函数必须来自实际检索结果；没检索到就写 ❌ 或 ❓，不编造路径。发现 spec 与代码不一致时显式报告分歧，判 ❓，不擅自选边。

### Step 8 · 输出覆盖矩阵与待补清单

按模板第二部分输出：覆盖矩阵、三类场景各自的覆盖率统计、所有 ⚠️ / ❌ 的待补清单（按场景编号排序）、❓ 项所需的补充信息。代码不可读时，不输出覆盖矩阵，改为输出「可执行的检查表 + 每项需要的检索式」。覆盖矩阵、待补清单、测试用例映射一律引用同一场景 ID。

## 硬约束

- 三类场景必须都有输出；边界与特殊不得混为一类。
- 每条 Phase 1 场景必须有「来源」和「代码检查线索」；每条 Phase 2 判定必须有证据或明确标 ❓。
- **禁止臆造 spec 内容**：字段、状态、枚举、阈值、错误码、接口名只能来自实际读到的文档；未提供的标【未提供】。没读过文档不得声称读过。
- **来源二分**：spec 明写标 `[Source]` / `[Source+Derived]`，维度库补齐标 `[Inferred]` 并指到具体维度组；禁止把推断写成规格结论。
- **排除必须留痕**：只有 spec 明确声明（由公共组件处理 / 不在范围 / 沿用现有逻辑）才可排除，且必须写进 Scope Reduction Log 并附 spec 原文依据；禁止静默省略，禁止因「看起来不重要」跳过。
- **规格矛盾不拍板**：模糊词、规则冲突、示例与规则冲突一律标 `⚠️ SPEC AMBIGUITY`，按更严解释生成场景，把选项及各自影响写进「待确认问题」。
- **ID 稳定且双向可追溯**：spec 的 AC / FR 编号原样保留；场景 ID 一经分配不改号、不复用；Phase 1 / Phase 2 / 测试用例统一引用同一 ID；每条场景可回溯到 spec 条目或维度组。
- 禁止用「应报错」「需处理」这类无判定标准的描述；预期结果要可观察、可判定。
- 禁止把「重复数据」当成一种场景：区分完全重复、同键不同值、格式差异重复。
- 禁止笼统写「历史数据」：区分无数据 / 有同类 / 有冲突 / 软删 / 已归档 / 跨期 / 脏数据。
- Phase 2 不预测缺陷、不做风险评估，只做覆盖度核验；不做 PRD 质量评分或文档改写建议。
- 业务口径不确定的进【待确认】，给出选项及影响，不替业务拍板。

## 用法示例

**输入为一段需求描述**：「会员等级改为按近 12 个月消费额自动升降级」。

- **业务主场景**：达标升级、未达标降级、权益按新等级刷新；入口包括页面、接口、每日定时任务。
- **边界场景**：消费额刚好等于阈值 / 阈值±1；近 12 个月恰好 1 条 / 0 条记录；跨月首日与月末；首次定级；单次批量上限。
- **特殊场景**：历史会员没有近 12 个月数据；定时任务与手动调整同日发生；任务重跑；批量中途失败；权益缓存未刷新；老客户端读新等级字段；开关关闭时走旧行为；进行中的升降级单据。
- **Phase 2**：逐条检索等级计算分支、阈值常量、判空、幂等键、缓存 key、事务边界、权限过滤，标注 ✅ / ⚠️ / ❌ / ❓ 并附证据。

**输入为一份 spec 文档**（例：`docs/specs/member-level.md`）：

- `[Source] spec §2 / AC-03` → 「连续 12 个月消费额 ≥ 10000 自动升级」映射为 B01，附 spec 原文要点。
- `[Source+Derived] spec §4 阈值 10000` → 派生 E01（9999 / 10000 / 10001），注明派生动作。
- `[Inferred] F3-重复与重试` → 「每日任务重跑」，附代码线索「幂等键 / job_log 判重」；spec 未写，明确标注。
- `Spec Exclusion` → spec §6 写「入参校验由公共校验框架统一处理」，字段格式类场景不展开，但保留一条核对项「确认新接口接入了该框架」，记入 Scope Reduction Log。
- `⚠️ SPEC AMBIGUITY` → spec §3「等级只升不降」与 §5「未达标自动降级」冲突，按更严解释（不降级）生成一条场景，两个选项及影响进 Q01。
- Phase 2 全部沿用 `B01 / E01 / S01 …`，不另编号。
